# 项目文档清单 — 给"1 个开发者 + 1 个 IT"的项目

> **不是互联网大厂完整理论**,是给中小团队(几个开发者 + 1-2 个 IT)的实用清单。
> 核心:**先想清楚"谁会在什么时候看"**,再决定写哪一类。不要全写。

---

## 选自己需要的 — 不是全写

每类文档的价值 = **(看它的人 × 看它的频率 × 不看会出错的概率)**。

如果没人看,或者看了不会改变行动,就别写。

---

## 按受众 / 场景分

### 1. 新成员第 1 天要看的(必读)

| 文档 | 作用 | 何时写 |
|---|---|---|
| **README** | 项目干嘛、技术栈、快速启动 3 步;新成员入口 | 项目第 1 周 |
| **架构文档** | 模块划分、数据流、技术选型理由(几句话就行) | 第 1 次技术选型后 |
| **术语表 / Glossary** | 业务名词统一,避免代码里"图号/图名"混用 | 业务功能第一个写之前 |
| **配置说明** | `appsettings.json` 每一项的含义、默认值 | 配置稳定后 |

### 2. 开发者改代码时要看

| 文档 | 作用 | 何时写 |
|---|---|---|
| **开发规范** | 命名约定、错误处理模式、code review 流程 | 2-3 个开发者协作前 |
| **ADR(架构决策记录)** | "为什么选 SqlSugar" / "为什么用 unique index 不用 SERIALIZABLE" 等技术决策 | 每个明显决策后 |
| **API 接口文档(Swagger/OpenAPI)** | HTTP API 调用例子 | 后端是公开 HTTP API 时 |

### 3. IT 第 1 次部署要看

| 文档 | 作用 | 何时写 |
|---|---|---|
| **部署指南** | IIS / Linux / Docker 步骤、环境依赖、证书 | 第 1 次部署前 |
| **配置说明**(同上) | 哪些项 `appsettings.Production.json` 必须填 | 同上 |
| **上线后必查清单** | "部署完逐项 ✓ 才能算上线" | 每次大版本上线前 |

### 4. IT 故障时要看(应急)

| 文档 | 作用 | 何时写 |
|---|---|---|
| **运维手册 / Runbook** | 常见故障(F1/F2/F3)+ 处理步骤、日志位置 | 部署后累积,半年内补齐 |
| **监控告警** | 哪些指标异常 = 需要处理 | 有监控体系时(没监控 = 至少有"手工怎么发现"一段)|
| **灾备与回滚** | 数据库备份策略、版本回滚步骤 | 第 1 次部署后 1 个月内 |
| **FAQ** | 重复被问的问题写下来 | 累积,每季度整理 |

### 5. 管理层(可选,看团队规模)

| 文档 | 作用 | 何时写 |
|---|---|---|
| **路线图 / Roadmap** | 下季度打算做什么 | 有计划时 |
| **故障复盘 / Postmortem** | 每次线上事故的根因 + 预防措施 | 出事故后 |
| **安全审计** | 代码 review + 漏洞扫描 | 每年 1 次,或重大改动前 |

### 6. 社区 / 法律(看情况)

| 文档 | 作用 | 何时写 |
|---|---|---|
| **LICENSE** | 开源协议 | 项目开源就写 |
| **SECURITY.md** | 漏洞披露流程 | 给外部研究者看 |
| **CONTRIBUTING** | 外部贡献者指南 | 有外部贡献者 |

## 按生命周期分的时间表

```
项目开通第 1 周
  → README + 术语表 + 架构(草稿)
  → LICENSE / SECURITY / CONTRIBUTING(如果适用)

第 1 个技术选型决策
  → 第 1 个 ADR

每次明显技术决策
  → 新 ADR

第 1 次部署
  → 部署指南 + 配置说明 + 上线后必查清单

稳定运行 1-3 个月
  → 运维手册 / Runbook(累积)
  → FAQ(累积)

每次重大 Bug 修完
  → 顺手改相关文档(规则、TODO)

每出 1 次事故
  → 故障复盘

每季度
  → FAQ 整理 + CHANGELOG 更新

每年
  → 安全审计 / 依赖升级评估
```

## 文档放哪里

| 位置 | 放什么 |
|---|---|
| 仓库根 `README.md`、`CHANGELOG.md`、`CONTRIBUTING.md`、`LICENSE`、`SECURITY.md` | 顶层入口,GitHub 直接显示 |
| 仓库根 `docs/` | 多项目共享的文档(如跨项目代码审查报告) |
| 项目子目录 `docs/` | 该项目内部文档(架构、部署、ADR、Runbook) |
| 项目 Wiki (GitHub / Confluence) | **不建议** — 跟代码分离就过期 |
| 知乎 / 内部站 | **不建议** — 散在很多地方,后来人找不到 |

**金科玉律**:**文档跟代码一起 commit**,改代码顺手改文档,`git log` 能看到对应 commit。

---

## 不要做(常见坑)

1. **为写文档而写** — 没人看=浪费。删。
2. **写在 Wiki 里** — 跟代码分开放就过期。强制 Markdown + 仓库内。
3. **在 docs/ 放 PPT / Word / PDF** — 转成 Markdown 才有 diff、有 blame、有检索。
4. **过时文档直接删** — 加 `**[deprecated]** 老版本,x.x 后不再维护`,告诉读者去哪看新版本。文档历史也是知识。
5. **在 README 堆所有信息** — README 是入口,详情丢 docs/。README 50-100 行差不多了。
6. **纯代码注释替代文档** — 注释说"怎么实现",文档说"为什么这样设计 + 怎么用"。两者不重叠。
7. **凭兴趣写 ADR** — ADR 是"决策记录",不是为了写而写。每个 ADR 必须对应一个**具体的决策**(选 SqlSugar / 选 X 库 / 不做 Y 功能...)。否则不开 ADR 也没问题。

---

## 让文档真被用起来(机制建议)

1. **新成员 onboarding checklist** — 列出"第 1 周必须读完的 4 个文档",不是"想看啥看啥"。
2. **半年度审查** — 列文档清单 + 检查覆盖度 + 删/改/补。
3. **重大 Bug 顺手改文档** — 修了一个导致用户搞错的 bug,说明 FAQ/开发规范没写或写错,**跟着改**。
4. **CHANGELOG 强制写** — 每个 fix 都要在 commit message 或者 PR 里有个对应行,定期合并进 CHANGELOG。

## 一句话总结

**写文档的核心不是"该写多少",而是"谁会在什么时候看"**。
没人看的文档 = 浪费。
真用的场景,文档就要写得让"那个人"看得懂。
